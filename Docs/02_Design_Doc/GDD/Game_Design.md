# motheffect：游戏策划案

版本 v0.5　日期 2026-10-03　游戏名 motheffect　开发者 单人  
平台建议 Windows PC　引擎 UE 5.8　开发方式 C++ 与蓝图混合

本策划案把已确定的创意落实为可在本次 GameJam 中验证和交付的版本。游戏名 motheffect，风格魔法朋克，采用已建立的 MothEffect 第三人称模板工程作为建议实现起点。玩家以第三人称越肩视角射击敌人，把敌人原地掉落的机关拾取、投掷，再通过射击激活。交互规则以 [道具与交互规则](Device_Interaction_Rules.md) 为准，所有初始数值以 [玩法参数基线](Gameplay_Parameters.json) 为准。本文件负责体验目标与内容边界，不重复技术接口和参数表。

## 1A 魔法朋克呈现建议

场地以金属结构、管线、符文和晶核驱动的机械工坊呈现。主武器表现为魔导步枪，敌人可采用魔导构装体，死亡后留下带封印的机关核心。D01 用符文活塞/地脉柱表达弹射，D02 用晶核封印破裂表达爆炸，D03 用咒印发射器表达定向火线；这是表现层映射，沿用同一套触发与伤害规则。

蛾翼轮廓、灯光与逐级亮起的符文可呼应名称与连锁主题。它们只作为图标、材质和反馈提案，不增加蛾群 AI、飞行角色或召唤机制。具体资源规格见 [关卡、界面与资源规格](Level_UI_Asset_Specification.md)。

## 2 核心体验

一句话介绍：在会不断留下机关的战场中，击败敌人，搬运机关，用一枪启动自己布置的连锁攻击。

玩家主要做四种判断：在哪里击败敌人，留下的机关能影响谁，投掷到什么位置，以及在什么时候开枪启动。直接射击提供基本生存能力；机关提供对位置、方向与时机的利用空间。

主题表达来自同一套规则的组合。例如柱子可以抬起炸弹，发射器的弹丸可以击中这枚炸弹，爆炸又可以推开另一台正在发射的装置。结果应来自实际位置、运动与命中，而不是某个预写的组合技能。

判定设计成立的观察项：玩家能够主动重复一条连锁；换一个位置会产生不同结果；玩家能解释成功或失败的原因。华丽特效本身不作为机制成立的证据。

## 3 核心循环

击败敌人 → 观察其掉落 → 拾取或直接利用 → 投掷到攻击位置 → 射击启动 → 连锁改变战场 → 完成当前波次。

场内原地掉落使击杀位置有意义。三类敌人变体采用固定掉落，帮助玩家提前规划。P0 不采用随机掉落；敌人的外观、死亡后的道具外形与图标保持对应。

## 4 玩家与基础战斗

采用官方 Third Person 模板人物和基础移动动画作为起点，加入越肩相机、一把步枪、血量和跳跃。角色持枪姿态与投掷表现先用能看懂的简化动作完成，专门制作动画不作为第一轮原型的前置工作。

| 情境 | 操作建议 | 行为 |
| --- | --- | --- |
| 普通状态 | WASD 和鼠标 | 移动与视角 |
| 普通状态 | 右键 | 越肩瞄准 |
| 普通状态 | 左键 | 步枪射击，受弹药与间隔限制 |
| 普通状态 | R | 换弹，备用弹药不设耗尽限制 |
| 有可拾取道具 | E | 拾取准星附近、可见且在范围内的未激活道具 |
| 持有道具 | E | 安全放下，有空间才执行 |
| 持有道具 | 左键 | 投掷一次，之后释放左键，再次按下才恢复射击 |
| 持有道具 | 右键和鼠标 | 调整投掷方向 |
| 移动状态 | Space 和 Shift | 跳跃与跑步 |
| 菜单状态 | Esc | 暂停，继续或重新开始 |

持有道具时主枪不射击。投掷后恢复枪械，需避免同一次左键输入自动射中刚抛出的道具。被弹射期间仍能控制视角和射击；空中移动能力与落地反馈作为原型调参项。建议初版无坠落伤害，减少弹射玩法被惩罚的情况。

## 5 三类机关

D01 弹射装置，在激活位置下方的可承托地面起柱，弹起柱子作用范围内的角色和可移动道具。

D02 爆炸装置，在被击中的当前位置产生爆炸，造成范围伤害和推力。地面和空中共用同一规则。

D03 发射装置，在命中位置启动，锁定启动弹丸的世界飞行方向，持续发射短时弹丸。装置保持重力与移动，形成移动火线。

以上为建议规则的概括。携带状态、重复命中、墙壁阻挡、过期和数量上限必须按 [道具与交互规则](Device_Interaction_Rules.md) 实现。地面与空中的区别来自空间条件，不另开六套技能。

## 6 敌人与关卡流程

P0 使用一套带明显攻击预警的射击 AI。三种颜色加形状标记的变体分别固定掉落 D01、D02、D03；它们在首版中可以共享移动、瞄准、射击与血量。差异化攻击留在 P1。

完整流程：标题与操作说明 → 分步教学 → 三波战斗 → 胜利或失败 → 重开。每波开始前有短暂准备阶段，玩家可以查看和调整未激活机关。清完存活敌人后进入下一波；胜负转换时立即停止伤害、生成和机关工作，避免结算后继续死亡。

大型场地采用一张连续竞技场，按三片交互区域组织。灰盒尺寸及敌人数量见 [关卡、界面与资源规格](Level_UI_Asset_Specification.md)。验证房是制作工具，不替代正式大型场地的已确认意图。

## 7 范围与优先级

| 优先级 | 交付内容 | 完成判据 |
| --- | --- | --- |
| P0 核心 | 越肩射击、拾取投掷、空中激活、三种机关、机关之间的真实连锁 | G1 与 G2 门槛通过 |
| P0 完整体验 | 一图、一枪、一套 AI 三外观、教学、三波、胜负、重开、设置与提示 | G3 门槛通过 |
| P0 提交 | 可运行 Windows 包、崩溃与阻断缺陷清零、平台材料与审核 | G4 门槛通过 |
| P1 扩展 | 冲撞 AI、五波扩展、投掷轨迹预览、更丰富特效、计分挑战 | 剩余时间充足且 P0 验收后取一至两项 |
| P2 延期 | 多地图、Boss、成长树、背包、多枪、联网、移动端、专门动画制作 | 本次不纳入任务工时 |

降范围时保留三种机关、投掷空中激活与真实连锁；优先减少美术、额外敌人行为和波次扩展。否则核心创意会退化为普通波次射击。

## 8 早期验证与设计冻结

G0 从现有模板工程确认环境能编译并打包，工程创建子项已完成。G1 验证投掷、空中射击与方向理解。G2 验证同一规则在不同布局中产生连锁。G3 验证三波闭环。G4 核查提交包与审核状态。

G2 通过后冻结道具类型、状态与接口；参数仍可调整。修改规则时，先在 [设计决策](../TDD/Decisions/Design_Decisions.md) 记录原因、影响的规则 ID 和测试 ID，再更新权威文档及实现。冻结指减少变化，并不要求为常规修改向用户重复请求批准。

原型失败时先定位相机、判定、反馈或规则问题；当 G1 尚未成立时，不进入完整场景美术制作。文档不能保证完全免返工，但能把不确定性集中在前期验证。

## 9 成功标准与交付事实

设计目标：第一次试玩能理解三种道具；能够完成一次有意安排的空中激活；看到并尝试复现至少一种连锁；可以从标题进入战斗并完成胜负重开。

这些是待验证目标。目前已核对模板工程文件存在，尚未验证本作自定义玩法、试玩或性能结果。开发任务、验收方法和证据格式分别见 [开发任务与排期](../../05_Development_Guide/Development_Plan.md) 与 [测试计划与验收](../../06_Test_Doc/Test_Plan.md)。
