## 2. 本地候选包与发布检查顺序

下列为实际投稿的执行顺序；本次 Docs 同步未执行包体上传、提审或发布。每项当前状态均为“待执行”。

1. 冻结候选包的代码、资产与 [玩法参数基线](../02_Design_Doc/GDD/Gameplay_Parameters.json) 参数，标明版本和已知 S2/S3 限制；查清 S0/S1 与未执行的核心规则/本地包测试为零。TC29 平台部分在上传后按第 6 步完成，未通过时不提审。
2. 完整 Windows 打包，确认入口地图、主竞技场与验证所需运行资源正确包含；公开包不含开发专用测试入口、调试作弊开关或不必要符号文件。
3. 把**完整运行目录**压为后台接受的 zip/7z；不要只取单个 exe。重新解压到独立目录，关闭编辑器，执行 TC29 的本地部分；准备正确入口 exe 相对路径，遵循实际后台示例。
4. 用报名账号确认个人厂商认证状态、参赛项目归属；按对应后台教程选择 Windows 常规发布/提供游玩等实际配置，填写游戏资料、当前版本说明、物料、真实资产说明；不要宣称未实现功能。
5. 上传最终候选包，保存包体标识与校验信息，等待解析完成；在后台核对实际可执行文件路径及版本设置。首次或更新包都按实际后台要求填写，更新版号递增。
6. 执行平台自测，确认**上传的相同包体**能启动、接受输入、完成空中启动和三波、退出重开；不能只凭本地测试跳过这一步。
7. 核对报名投稿选项与游戏发布状态；依据实际接入情况与对应 PC 后台教程填写防沉迷等配置。内容全部就绪后由开发者提交审核，记录提交时间、版本、项目与后台状态。
8. 查看站内信和后台审核结果。被退回时记录具体原因，只改必要项，重新打包/验收受影响内容，再上传提审；旧审核结果不自动覆盖新包。
9. 在 10/21 12:00 前确认官方状态确为通过审核且参赛关联有效，保存证据。游戏实际可下载/游玩后，从平台提供的包再验证启动与核心操作。

新增版本会重新影响审核与时间，10/18–20 只做必要修复。提交时间、审核完成时间和可游玩状态分别记录；只有上传记录不能判定 G4 或有效投稿完成。
